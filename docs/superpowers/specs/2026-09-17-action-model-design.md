# Action model, built-in set, actions.toml merge, proposal schema registry

Status: **approved** (owner asleep; this plan is written against issue #23,
issue #199's `group` field, and issue #197 part 2, all already scoped by the
owner in the issue bodies and the 2026-09-16 expansion plan §6. Treated as
pre-approved per the overnight-agent instructions; the owner reviews on
waking.)

Scope: the `Action` data model, the built-in catalogue (one action: "Check
my work"), the `actions.toml` merge/override/disable rules, and the proposal
JSON-schema registry. Out of scope: the palette (#25), the intent router,
any new executor, the settings Actions page (#48), and moving
`ui.show_difficulty`'s Settings checkbox anywhere (#197 part 2 only adds the
action-level option; the config-level toggle is untouched).

## Why a design doc (rule 12)

This adds a new module (`actions/`) and changes what decides the system
prompt and JSON schema sent for the one action Wingman runs today, which is
architectural per AGENTS.md rule 12 and CONTRIBUTING.md's "spec-first"
section. It is short because the shape is already pinned by the expansion
plan §6 and CONTRIBUTING.md's worked example; this fills in the concrete
Rust types, the TOML shape, and the merge/precedence rules those two
documents leave implicit.

## Types

`src/actions/mod.rs`:

```rust
pub struct Action {
    pub id: String,
    pub name: String,
    pub group: Option<String>,         // #199, e.g. Some("Study")
    pub inputs: Vec<InputKind>,
    pub proposal: String,              // schema-registry key, e.g. "verdict"
    pub executor: String,              // "none" is the only implemented value today
    pub confirm: bool,
    pub prompt: String,
    pub prefer: Prefer,                // { mode: String }, default "auto"
    pub hotkey: Option<ActionHotkey>,  // vk/ctrl/shift/alt/win, inert until the palette exists
    pub rate_difficulty: bool,         // #197 part 2, default false
    pub enabled: bool,                 // default true
}

pub enum InputKind { Screen, Window, Region, Selection, Clipboard, Text, Uia, Context }

pub struct ActionsFile {
    pub actions: Vec<Action>,
    pub disabled_groups: Vec<String>,  // #199
}
```

`Action` and its nested types derive `Deserialize`/`Serialize` with
`#[serde(deny_unknown_fields)]` on `Action`, `Prefer` and `ActionHotkey`: a
typo'd key in a hand-edited `actions.toml` must fail to parse with a message
naming the field, not be silently ignored (#23's Done-when: "a malformed
action file is reported in a card, not a crash" -- the card comes for free,
see "Error path" below).

`InputKind` is a closed enum (`serde(rename_all = "snake_case")`), not a bare
`String`: an action naming an input Wingman doesn't gather yet is exactly
the kind of typo `deny_unknown_fields` on `Action` cannot catch on its own
(the field name `inputs` is spelled right; the *value* `"screeen"` is not).

## TOML shape

Matches CONTRIBUTING.md's worked example field-for-field, plus `group` and
`rate_difficulty`:

```toml
[[actions]]
id              = "check-my-work"
name            = "Check my work"
group           = "Study"
inputs          = ["screen"]
proposal        = "verdict"
executor        = "none"
confirm         = false
prompt          = "..."
rate_difficulty = false
enabled         = true

[prefer]
mode = "auto"

disabled_groups = ["Finance"]
```

`actions.example.toml` is generated by a drift test
(`src/actions_example.rs`, mirroring `src/config_example.rs`) from
`actions::builtin_actions()`, so it cannot drift from what the code actually
parses. `UPDATE_EXAMPLES=1 cargo test actions_example` regenerates it.

## Merge rule: replace-by-id, not per-field

A user `actions.toml` entry whose `id` matches a built-in **replaces it
wholesale** -- every field, not a per-field overlay. This is deliberately
the simpler of the two options CONTRIBUTING.md leaves open:

- Per-field merge (only the keys present in the user's TOML table override
  the built-in) needs an `Option<T>` wrapper on every field to distinguish
  "not set" from "set to the type's default" (`confirm = false` would
  otherwise be indistinguishable from "not specified"), doubling the type
  count for no behaviour Phase 2 needs.
- Replace-by-id matches CONTRIBUTING's own worked example, which is always a
  complete `[[actions]]` block, and keeps `deny_unknown_fields` meaningful
  without a second, all-`Option` shadow struct.

A user entry whose `id` matches no built-in is a **new** action, appended
after the built-ins in file order. Nothing in Phase 2 gives a new user
action anywhere to run (no palette, no non-`"none"` executor), so this is
inert today but not rejected -- rejecting it would make `actions.toml`
useless for the one thing a contributor testing a new catalogue action
before it ships actually wants to do.

## Group disable (#199)

`disabled_groups` is a flat list of group names. An action whose `group` is
in that list is filtered out, same as `enabled = false`. Both checks run
*after* merge, so a user can simultaneously override a built-in's fields and
have it hidden by its group (the override still matters if the group is
re-enabled later without touching the action's own `enabled` flag).

## Origin tracking, and why the effective prompt needs it

The one behavioural rule this issue must not break: **no user-visible
change to what "Check my work" does today**, except where explicitly
scoped. Today's system prompt is `config.ui.prompt` (edited directly in
`config.toml`, no Settings UI round-trip needed for that field). The new
built-in `Action::prompt` is also populated (with the same
`provider::DEFAULT_PROMPT` text), because the `Action` struct requires it
and because it is *the* value an `actions.toml` override changes.

Two independently-live places can supply "the prompt" for the same action,
so precedence has to be decided, and it cannot be "whichever is loaded
last" without breaking a user who has only ever touched `config.toml`
(everyone, before this issue). The rule:

```rust
pub enum Origin { Builtin, User }   // did actions.toml override this id?

effective_prompt = match origin {
    Origin::User    => resolved_action.prompt,  // actions.toml wins outright
    Origin::Builtin => config.ui.prompt,         // unchanged from today
};
```

`merge_actions` returns `Vec<Resolved>` (`{ action: Action, origin: Origin
}`), so this is a plain enum comparison, never a text comparison against
`DEFAULT_PROMPT` (which would misfire the moment a user's `actions.toml`
override happens to paste back the exact default text, or the moment
`DEFAULT_PROMPT` itself is edited). `Origin::User` is recorded at merge time,
the one place that genuinely knows whether an id came from the user file.

The same reasoning does **not** apply to difficulty: `rate_difficulty` and
`config.ui.show_difficulty` are independent booleans answering the same
question ("send the rubric"), not two candidate values for the same field,
so they simply OR:

```rust
want_difficulty = config.ui.show_difficulty || resolved_action.action.rate_difficulty;
```

Both default `false`, so a fresh install and every existing config.toml
(`show_difficulty` already defaulted to `false` as of #197 part 1, commit
`d88f78b`) still send no rubric -- identical to today. Issue #197's "the
global toggle keeps working as an override for existing users" is exactly
this OR: whichever install left `show_difficulty = true` in an old config
keeps getting the badge with zero actions.toml involvement.

## Proposal schema registry

`src/actions/schema.rs`:

```rust
pub fn schema_for(proposal: &str, rate_difficulty: bool) -> Option<Value> {
    match proposal {
        "verdict" => Some(crate::provider::common::answer_schema(rate_difficulty)),
        _ => None,
    }
}
```

`"verdict"` is the only registered kind. It delegates to the existing
`provider::common::answer_schema` (already `pub(crate)`, already the one
place `detail`-before-`headline`-before-`difficulty` ordering lives) rather
than duplicating that JSON -- this is what makes the golden test in
`provider/mod.rs` (physics_request's schema, captured *before* this refactor
touches `physics_request`) trivially byte-identical after: the registry is a
thin named lookup over the same function, not a second schema. The other
proposal kinds CONTRIBUTING.md names (`text_answer`, `calendar_event`,
`form_fill`, `text_review`) return `None` -- they land with their own
catalogue actions in later phases (expansion plan §6, "Action catalogue"),
each adding one arm here.

## What changes in `provider/mod.rs`

`physics_request`'s body swaps its one `common::answer_schema(want_difficulty)`
call for `crate::actions::schema::schema_for("verdict", want_difficulty)`
(`.expect(...)`, since `"verdict"` is always registered) -- the only line
that changes, proven identical by the golden test. Its signature, its
prompt/images/effort/max_tokens construction, and `parse_answer` are
untouched. `provider::mod` and `actions::schema` reference each other
(`actions::schema` calls into `provider::common`, `provider::mod` calls into
`actions::schema`); both are modules of the same crate, so this is an
ordinary two-way function call, not a build-graph cycle.

## What changes in `app.rs`

`worker()` (the function that already runs on the spawned request thread,
never the main thread) gains one step before building `physics_request`:
load and resolve the action catalog, find `"check-my-work"`, and derive the
effective prompt and difficulty flag per the rules above. `ask()`'s call
site is unchanged -- it already clones `config.ui.prompt` and
`config.ui.show_difficulty` onto the worker thread; those become the
`Builtin`-path fallback values `worker` consults instead of the only values.

A load or parse failure (`actions::load_actions()` returning `Err`, e.g. a
malformed `actions.toml`, or the default action missing/disabled) is
returned from `worker()` as an `Err`, which `ask()`'s existing
`.map_err(|e| format!("{e:#}"))` -> `PostMessageW(WM_APP_RESULT, ...)` ->
`on_result` -> `record_last` -> `show_error` path already turns into a card
with no new UI code (rule 7; this is the "reported in a card, not a crash"
half of #23's Done-when -- the crash-avoidance is `?`/`Result` all the way
through, same as every other worker failure today).

## Paths and test isolation (rule 9)

`actions::path()` mirrors `Config::path()`:
`%APPDATA%\Wingman\actions.toml`, via the same
`known_folder::roaming_app_data()`. Only `actions::load_actions()` (the
real-path entry point `app.rs` calls) touches it. Every test goes through
`actions::load_actions_from(&Path)` against a scratch directory, the same
split `Config::load` / `Config::load_from` already uses.

## What stays out of scope

- No executor other than `"none"` exists; `executor` is validated as present
  but not resolved to anything.
- No palette, no intent router, no hotkey wiring for `Action::hotkey` (dead
  data until #25/the router land) -- unit-tested for round-trip only.
- No Settings UI for actions (#48) or for `disabled_groups`; both are
  hand-edited TOML for now, same maturity level `providers.compat` had
  before its own settings page.
- `ui.show_difficulty`'s Settings checkbox is not moved, relabelled, or
  duplicated; #197 part 2 is satisfied by the OR rule above, not by UI
  surgery.
